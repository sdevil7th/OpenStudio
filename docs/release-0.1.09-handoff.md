# OpenStudio 0.1.09 release handoff

The application release branch is `main`. [App PR #37](https://github.com/sdevil7th/OpenStudio/pull/37) brings `develop` into `main`. Merging runs **Verify**. Creating the separate numeric tag `v0.1.09` starts **Release**, including the two Store paths. The current public baseline is [v0.1.08](https://github.com/sdevil7th/OpenStudio/releases/tag/v0.1.08).

## Before tagging

1. **Publisher decision.** Obtain Canonical's actual classic-confinement decision for `openstudio`. The review bot queued the request. The queue message does not grant approval. Record the reviewer's decision permalink in `OPENSTUDIO_SNAP_CLASSIC_APPROVAL_URL` after approval. Leave both Store switches enabled. A missing approval blocks GitHub publication, website dispatch and both Store submissions. [Canonical review](https://forum.snapcraft.io/t/guidance-on-classic-confinement-eligibility-for-openstudio/54087)
2. **App merge.** Merge PR #37 through the protected `main` branch. Fetch the merged commit, record its SHA and wait for the **Verify** run on that SHA. Confirm the installed Windows, Linux, Snap and universal Mac jobs and the WACK report. Preserve the two optional WACK findings and the accepted loaded eight-sample limitation. Apple Developer ID signing and notarization remain unqualified.
3. **Website merge.** Review [website PR #32](https://github.com/sdevil7th/OpenStudioWebsite/pull/32), merge it into the website's `develop`, then promote the reviewed website commit through a PR to its default `main` branch. The release dispatch uses the website default branch. Keep the download version and feeds on the published GitHub version until the app release actually exists.
4. **Version and inputs.** Review the exact `v0.1.08` to merged-SHA changes and validate `docs/releases/0.1.09.md` with `python tools/validate-release-notes.py --version 0.1.09`. Review the plain-text Store summary including its full-notes link. Confirm the runtime release variables still select the reviewed Windows/macOS `ai-runtime-v0.0.16` and Linux `ai-runtime-linux-v0.0.14` assets. Keep the update signing seed and website dispatch credential available. Both Store environments are restricted to `v*` tags. The protected tag-time Microsoft preflight must confirm account access, the published baseline, the package and absence of an unrelated draft.

## When the release owner elects to ship

5. **Tag the verified commit once.** Confirm `v0.1.09` is unused on the remote. Create the annotated tag at the recorded merged SHA and push that tag alone. The normal release command sequence is `git tag -a v0.1.09 <verified-main-sha> -m "OpenStudio 0.1.09"`, then `git push origin refs/tags/v0.1.09`. Do not move an existing tag to correct a failed release.
6. **Watch the tag's Release run.** It rebuilds the candidate, reruns WACK on the exact tag-built MSIX and installs and qualifies the Snap. It performs read-only preflights against both Stores. Only after both succeed does it publish the GitHub assets and signed updater feeds. Keep the run URL, tag SHA, package hashes, tag WACK report and preflight reports.
7. **Microsoft Store.** `submit-store` updates product `9N3MQ442VXGW`, using package identity `SouravDas.OpenStudio` and version `0.1.9.0`. It preserves listing artwork, other languages, pricing and audience, writes the reviewed English release notes and submits the package for certification. The tag-specific publishing mode is `Immediate` after Microsoft certifies it. Verify the submission reaches **Published**, then check the public package version, notes and a Store-installed upgrade from `0.1.8.0`. [Microsoft listing](https://apps.microsoft.com/detail/9N3MQ442VXGW)
8. **Snap Store / Ubuntu App Center.** `submit-snap` uploads the qualified bytes to stable. `sync-snap-listing` independently matches the Store revision hash, applies the tagged listing and reads it back. The logo and two reviewed native Linux screenshots are already saved. Compare the public stable revision, version, listing text, keywords, category, links and artwork to `packaging/snap/listing.json`. Install or refresh using Ubuntu App Center and confirm that Support opens separately. Enable a public Snap link on the website only after the storefront serves the expected stable package. [Storefront](https://snapcraft.io/openstudio) · [Listing metadata API](https://dashboard.snapcraft.io/docs/reference/v1/snap.html#managing-snap-metadata)
9. **Website and updater.** Monitor the independent `openstudio_release_published` dispatch and production Netlify deployment. Check the download page, GitHub release snapshot, stable and unqualified manifests, all three appcasts and the installer checksums against this release. Check the Linux with-Support archive and the optional AI runtime links. Store reviews and website deployment may complete at different times. [Download page](https://openstudio.org.in/download) · [Stable feed](https://openstudio.org.in/releases/stable/latest.json)

## Recovery

- A failed preflight leaves the release unpublished. Inspect the specific report, correct the cause and rerun eligible failed jobs for the same immutable tag and artifacts. A source change requires a new reviewed version and tag.
- If package upload or commitment times out, inspect Partner Center or the Snap dashboard before retrying. Preserve unrelated pending submissions. If only Snap metadata failed, rerun the listing job for the already released revision. It has no upload command.
- If website deployment fails, retain the existing production deployment. Retry the website release dispatch only while this tag is still the latest published desktop version, then verify the public feeds. Apple notarization and physical loopback latency need their own evidence.
